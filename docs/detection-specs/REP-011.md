## What the detection must establish

Catch one identity whose successive successful VPN logins come from places too far
apart to be reconciled with the time between them. Each login is ordinary on its
own. The signal is the implied travel speed between consecutive logins by the same
user.

## Why the obvious approaches miss it

- **Failed-login thresholds.** Every login here succeeds. A brute force or spray
  rule keyed on failures never fires.
- **Single-event reputation.** Each source address is one documentation-range
  address, and a new address alone is common for a travelling or mobile user.
- **Country allow or deny lists.** The logins can all come from countries the
  organisation allows. The anomaly is the sequence, not any one country.

## Data model

Held across the run (the correlation key) is `duser`. Varying per login are `src`,
the country tag, `rt`, and the address the VPN assigned (`tunnelip`).

| Logical field | FortiGate | PAN-OS `[Unverified]` | Check Point `[Unverified]` |
|---|---|---|---|
| identity | `duser` | `duser` | `duser` |
| source address | `src` | `src` | `src` |
| country tag | `FTNTFGTsrccountry` | `cs4` (`cs4Label=Source Region`) | `cs4` (`cs4Label=Source Region`) |
| assigned address | `FTNTFGTtunnelip` | `PanOSPrivateIPv4` | `office_mode_ip` |

The country tag is optional on every vendor and is present only because this
technique supplies it. In SCEN-003 the assigned address is the pivot from `duser`
to the host-keyed stages that follow.

## Detection logic (SIEM-neutral pseudocode)

```
window      := 2h                      # >= the longest preset window (60 min)
max_speed   := 900                     # km/h, the catalog's stated threshold
min_gap     := 60                      # s, ignore near-simultaneous reconnects

for each duser over the window, logins sorted by rt where action = success:
    for each consecutive pair (a, b):
        dt_h := (b.rt - a.rt) / 3600
        if b.rt - a.rt < min_gap:              continue
        d_km := DISTANCE(GEO(a), GEO(b))       # GEO from your enrichment, see below
        if d_km / dt_h > max_speed:
            alert(duser, a.src, b.src, d_km, dt_h)
```

`GEO()` is the load-bearing dependency. In production it is a GeoIP or ASN lookup
on `src`. In this lab it cannot be, because every `src` is a documentation-range
address with no real location.

## Setting the thresholds

Measured over 20 seeds at each preset. One user, one login per country in order,
and consecutive logins always carry different country tags.

| Preset | logins | countries | gap between logins | distance needed to exceed 900 km/h |
|---|---|---|---|---|
| low | 2 | 2 | 1800 s (window_min 60) | more than 450 km |
| medium | 3 | 3 | 600 s (window_min 30) | more than 150 km |
| high | 4 | 4 | 225 s (window_min 15) | more than 56.25 km |

The four country tags are the fictional Wadiya, Molvania, Genovia and Elbonia.
They have no coordinates. To exercise the rule, the lab owner supplies a distance
table for those four tags. Any table that puts every distinct pair more than
450 km apart fires all three presets. That table is a lab constant, not a
geography claim.

## False positives and tuning

`[Inference]` from general practice, not measured here. In production the large
false-positive sources are VPN egress and cloud proxies (the user appears where
the provider is), mobile carrier gateways, and IPv6 or ASN geolocation errors.
Allowlisting known corporate egress and requiring the identity provider to agree
are the usual mitigations.

This technique emits **no benign foil**. Its contract marks the negative as
unsupported, because a credible control needs real GeoIP and approved-travel
context, and a synthetic country string cannot supply that. Do not substitute a
supplied country string for a benign control (UAT plan, SIEM-09).

## Exercising this with Replicant

```bash
# The full stream in a file, to read the tags and gaps.
replicant run REP-011 --intensity high --to-file ./rep011.log --no-send

# Into the lab (two logins, about two minutes; see tasks/lab-test-runbook.md).
replicant run REP-011 --intensity low --duration 2m --anchor now \
  --host <lab-collector> --port 514 --transport udp

replicant validate REP-011 --tier plan
```

With `--duration`, the gap between logins shrinks with the window, so the distance
needed to exceed 900 km/h shrinks too. Recompute it from the run's validation card.

## What a green result proves, and does not

REP-011 is **parser-only**. A green result shows the rule reads `duser`, orders
logins, and applies a speed threshold to a distance it was given. It does not show
that the rule's GeoIP or ASN enrichment works, because the lab supplied the
geography. It also does not show the rule copes with real false-positive sources.
None are emitted.

It does **not** prove end-to-end delivery. Every timing and delivery claim in this
project is loopback-only until the first observed rule fire in a real SIEM.
