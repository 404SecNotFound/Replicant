## What the detection must establish

Catch the first time **anyone in the organisation** queries a domain. A name new to
one host is common (REP-008 covers that). A name no host has ever queried, reached
by one or two hosts, is the shape of first contact with freshly registered
infrastructure.

## Why the obvious approaches miss it

- **Per-host novelty.** Every host meets names it has not seen before every day.
  The signal needs organisation-wide history, not per-host history.
- **Reputation and blocklists.** A domain registered for one operation has no
  reputation yet.
- **Volume.** First contact is one or a few queries. Nothing about its rate stands
  out.

## Detection logic (SIEM-neutral pseudocode)

```
lookback   := 30d          # organisation-wide history (production starting point)
eval_every := 5m
max_hosts  := 2            # first contact is reached by few hosts

HISTORY := set of registered_domain(qname) seen from any src in the lookback,
           excluding the current evaluation interval

every eval_every, for each registered_domain(qname) in the current interval:
    if domain in HISTORY:                     continue
    hosts := distinct src querying domain in the interval
    if len(hosts) <= max_hosts:
        alert(domain, hosts, first rt)
    add domain to HISTORY
```

In production the cited detector (PREDATOR) also scores registration age from
WHOIS. That stage cannot be exercised here and is not in the pseudocode.

## Setting the thresholds

Measured over 20 seeds at each preset.

| Preset | history names (each queried once) | hosts | history span | first-contact names | queries per new name | hosts per new name |
|---|---|---|---|---|---|---|
| low | 200 | 1 | about 55 min (window_min 60) | 1 | 1 | 1 |
| medium | 500 | 3 | about 25 min (window_min 30) | 3 | 1 | 1 |
| high | 800 | 8 | about 10 min (window_min 15) | 8 | 1 | 1 |

New names sit under the same parents as the history (`example.net`,
`sync.example.net`, `cdn.invalid`) and inside the history's label-length range, so
absence from the history is the only mark of novelty. `max_hosts = 2` clears every
preset.

## The lab problem this technique has today

This section is the most important part of the spec, and it is a finding, not a
setting.

1. **Every history name is itself a first contact.** Each one is queried once, by
   one host, under the same parents and length range as the new names. A SIEM that
   has never seen the history before treats all 200, 500 or 800 history names as
   first-seen and fires on them too.
2. **First contact arrives 2 to 18 seconds after the history ends** (measured).
   A rule cannot learn the history and then start evaluating in that gap, and a
   person cannot enable it by hand in that gap.
3. **Nothing in the evaluation window is a known name.** After the history ends,
   only new names are queried. So a rule that alerts on "any query after time T"
   scores exactly as well as real novelty logic, which means a green result cannot
   tell the two apart.

The only lab approach that works today is to prime the history first, by ingesting
a run's history phase before the rule is enabled, then send a second run whose new
names the rule has not seen. That second run is the hard part. With the same seed
it repeats the first run exactly, so its new names are no longer new. With a
different seed it brings a different history as well, which the rule has also never
seen.

The engine change that would fix this is outside this spec. A configurable pause
between history and first contact, plus repeat queries of known names during the
evaluation window, would let a rule learn and then be judged against known traffic.

## False positives and tuning

`[Inference]` from general practice, not measured here. New SaaS and CDN hostnames,
software update mirrors, and security tools resolving many names produce first
contacts daily. Restricting to registered domains (not every hostname), allowlisting
CDN and cloud parents, and pairing novelty with registration age are the usual
mitigations.

## What a green result proves, and does not

REP-020 is **parser-only**. Given a primed history, a green result shows the rule
keeps organisation-wide history and fires on a name absent from it. It does not
exercise registration-age scoring, because the names carry no registration data
and Replicant performs no WHOIS. Until the evaluation window carries known-name
traffic, it also cannot show the rule beats a plain time cutoff.

It does **not** prove end-to-end delivery. Every timing and delivery claim in this
project is loopback-only until the first observed rule fire in a real SIEM.
