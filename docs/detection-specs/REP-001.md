# Detection spec: NDR-C2-001, Periodic C2 callback (low-and-slow)

| | |
|---|---|
| Use case | UC-001 |
| Rule id | NDR-C2-001 |
| Technique | REP-001, Periodic C2 callback (low-and-slow) |
| ATT&CK | TA0011 Command and Control; T1071 (Application Layer Protocol), T1571 (Non-Standard Port) |
| Data source | FortiGate `traffic:forward`, `action=accept` (CEF signature 00013) |
| Transferability | **transfers** (a green result exercises this shipped logic, not just the parser) |

## What the detection must establish

Catch a beacon whose **individual sessions each look ordinary**, by keying on the
**regular interval** between callbacks rather than on the volume of any one of
them. A single small HTTPS session to an external host is unremarkable; a session
that repeats on a near-fixed cadence for hours is the signal.

## Why the obvious approaches miss it

- **Byte volume / thresholds.** Each callback is small (150-2000 bytes out; see
  the presets). A volume rule tuned to catch exfiltration never fires.
- **Reputation of a single event.** The destination is one synthetic-adversary IP
  contacted over 443/8443/8080/53, ports and a shape indistinguishable from
  normal egress on any single record.
- **Business-hours weighting.** The cadence has no business-hours weighting, so a
  time-of-day model does not separate it.

The discriminating feature is the **inter-arrival regularity** of the
`(src, dst, dpt)` tuple over a window.

## Data model

Held constant across a beacon (the correlation key): `src`, `dst`, `dpt`, `proto`.
Varying per callback: `rt` (event time), `out`/`in` (bytes), `externalId` (session
id). The rule groups on the held fields and analyses the sequence of `rt`.

## Detection logic (SIEM-neutral pseudocode)

```
window        := 6h                       # >= ~1.5x the longest run (REP-001 spans 2-4h)
min_callbacks := 8                        # enough samples to call a cadence
cv_max        := 0.25                     # inter-arrival regularity ceiling (see below)
byte_cv_max   := 0.8                      # callbacks cluster in a tight byte band

for each (src, dst, dpt) group over the window where proto in (6, 17):
    times   := sorted(rt for events in group)
    n       := len(times)
    if n < min_callbacks:            continue
    gaps    := [times[i+1] - times[i] for i in 0..n-2]
    cv      := stdev(gaps) / mean(gaps)                 # coefficient of variation
    out_cv  := stdev(out_bytes) / mean(out_bytes)
    if cv <= cv_max and out_cv <= byte_cv_max and dst not in KNOWN_GOOD_EGRESS:
        alert(src, dst, dpt, n, mean(gaps), cv)
```

## Setting the thresholds

The jitter in the emitted stream bounds `cv_max`. Jitter is uniform ±`jitter_pct`
about a fixed base, so the inter-arrival coefficient of variation is approximately
`(jitter_pct/100) / sqrt(3)`:

| Preset | interval | jitter | approx. inter-arrival CV | callbacks over the run |
|---|---|---|---|---|
| low | 300 s | ±20% | ~0.12 | ~48 in 4h |
| medium | 60 s | ±15% | ~0.09 | ~240 in 4h |
| high | 30 s | ±10% | ~0.06 | ~240 in 2h |

`cv_max = 0.25` clears all three presets with margin while excluding human traffic,
whose repeat-visit intervals to one host are far more irregular (CV typically well
above 0.5). `min_callbacks = 8` is comfortably below the smallest run's count, so a
`--duration` short of the full window still fires. Raise `cv_max` toward 0.3 only
if a real environment shows the rule missing jittered beacons; lower it if benign
periodic services slip through after the allowlisting below.

## False positives and tuning

**Legitimate software beacons are also regular**, and periodicity alone will flag
them: NTP (123), OS and application update checks, EDR/telemetry agents, and SaaS
keepalives are all low-and-slow by design. This is the load-bearing tuning step,
not an afterthought:

- **Allowlist known-good egress** (`KNOWN_GOOD_EGRESS`): update/telemetry/NTP
  destinations, by IP block, ASN, or resolved domain where the platform has it.
  Pair periodicity with destination newness or reputation for the residual.
- **Separate browsing to the same host.** The catalog's benign baseline is exact:
  browsing to the same destination shows *fewer* records, *far higher and more
  variable* out/in bytes, and *longer* session duration. The `min_callbacks` count
  and the `byte_cv_max` band exclude it without extra logic.

Measure the false-positive rate against benign traffic, not only the attack:
Replicant has no isolable foil for REP-001 (`emits_foil` is false), so use its
baseline peer or your own benign capture. Tune `KNOWN_GOOD_EGRESS` until the
regular benign beacons are quiet, then confirm the attack still fires.

## Exercising this with Replicant

```bash
# The interval IS the signal, so send it on the plan's own timeline.
replicant run REP-001 --intensity medium --anchor now --pace plan --speed 60 \
  --host <lab-collector> --port 514 --transport udp

# Or write the stream to a file to inspect the cadence without a collector.
replicant run REP-001 --intensity low --to-file ./rep001.log --no-send
```

Under `--pace plan` the callbacks leave at their own inter-arrival gaps (`--speed`
compresses the whole timeline, gaps included), which is what lets a cadence rule
see the interval. Under `--pace burst` the events arrive back to back and only the
`rt` field carries the spacing, usable for a rule that keys on parsed event time,
not on arrival time. The per-run validation card (`<manifest>.card.md`) prints the
`(src, dst, dpt)` pivot and the emitted window for this run.

## What a green result proves, and does not

REP-001 is **transfers**: the emitted stream carries the real inter-arrival and
byte structure this rule keys on, so a detection that fires here exercises the
shipped periodicity logic, not merely the CEF parser.

It does **not** prove end-to-end delivery. Every timing and delivery claim in this
project is loopback-only until the first observed rule fire in a real SIEM; until
then, "the rule fired on REP-001" means it fired on telemetry shaped like a beacon,
delivered on a path not yet observed working end to end.
